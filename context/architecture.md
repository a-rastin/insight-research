# Architecture Context

> **Scope:** This document describes the normative target architecture supported by the supplied INSIGHT materials. It does not claim that every prototype module already satisfies the target. Current deviations and unselected technologies are stated explicitly rather than inferred.

## Stack

| Layer | Technology | Role |
| --- | --- | --- |
| Architecture style | Independently runnable modules communicating through versioned internal REST APIs | Preserves module autonomy, independent testing, explicit contracts, and isolated data ownership. Modules are not merged and must not import one another's domain implementation. |
| Public edge | nginx with TLS on the VPS | Terminates TLS and owns HSTS, forwarded-header policy, request-size limits, and timeout policy. Only the unified gateway/router is publicly exposed. |
| Internal routing | Internal path router/gateway; implementation technology **not specified** | Routes public base paths to module-local processes and ports inside the unified container. Browser code must not contain hard-coded localhost service URLs. |
| Container runtime | One non-root Docker image containing multiple module processes | Runs through Docker Desktop on Windows and Docker on Ubuntu. A lightweight entrypoint/supervisor starts processes and propagates shutdown; the specific supervisor is **not specified**. VPS `systemd` manages only the container. |
| Python service runtime | Python with FastAPI, Uvicorn, and Pydantic | Used by Authentication, Dashboard, Add New Patient, Diagnosis, BN Manager, and Treatment Plan. Exact minimum Python versions differ in the supplied module documents and must remain module-pinned. |
| JavaScript service runtime | Node.js 18+; Express in the current Severity prototype | Used by Severity, Medical History, and Suicide Risk. DDI is currently a browser/static JavaScript module. |
| Clinical review UI | React + Vite | Used by Treatment Plan for psychiatrist review, structured plan editing, safety re-checking, and finalization. |
| Standalone module UI | Vanilla HTML, CSS, and JavaScript; Tailwind CDN in the current Severity prototype | Keeps Authentication, Dashboard, Add New Patient, Diagnosis, Severity, Medical History, BN Manager, and DDI independently operable where documented. UI implementation is module-local; shared domain logic is not imported across module roots. |
| Primary persistence | Module-owned SQLite databases with module-owned migrations and repository/adaptor seams | Default v1 persistence direction. Every module owns its schema, database file, migrations, validation, and lifecycle. Cross-module SQL and shared ORM models are prohibited. |
| Scale-up persistence | PostgreSQL, using separate databases or schemas and separate credentials per module | Upgrade path and optional Treatment Plan implementation. Cross-schema queries and foreign keys across module boundaries remain prohibited. |
| Prototype persistence requiring migration | JSON files in Severity and Medical History; browser `localStorage` in parts of Severity and DDI | Acceptable only for standalone prototype/testing behavior described by the source documents. These mechanisms are not production-ready PHI storage and must be replaced by authenticated, concurrency-safe, module-owned server persistence before clinical deployment. |
| API/data contracts | OpenAPI, JSON Schema, explicit module/interface/schema versions, UTC timestamps, UUIDs, ETags, idempotency keys, request/correlation identifiers, and RFC 9457-style problem responses | Makes all exchanged and persisted datasets machine-validatable and supports compatibility testing, concurrency control, traceability, and safe retries. |
| Authentication | Standalone FastAPI Authentication service; SQLite; bcrypt; HS256 JWT in an HttpOnly cookie; server-side session records; signed double-submit CSRF | Authentication is the sole source of truth for users, roles, session state, disclaimer gates, password-change gates, account status, and auth-domain audit events. |
| Bayesian inference | BN Manager 2.0; BIF 0.3 XML; `XSD.xml`; semantic validation; posterior evaluation | Owns the four canonical runtime Bayesian Networks and their registry. Runtime file loading is registry-controlled and path-safe. |
| DDI reasoning | Deterministic JavaScript interaction engine with a versioned knowledge base and medication-identity resolution | Checks every medication-instance pair, emits structured alerts, and fails closed on ambiguous or unknown identities. |
| Deployment verification | Independent module tests and unified Docker integration tests | A module must remain runnable and testable alone. Unified verification covers real HTTP integration, migrations, restart/recovery, backup/restore, TLS/security headers, and rollback. |

## System Boundaries

- `Modules/Authentication` — Sole owner of accounts, credentials, password hashes, roles, disclaimer versions and acceptances, login-failure controls, server-side sessions, session revocation, and authentication/security audit events. Other modules consume only its REST contract and must not decode its JWT or read its database.
- `Modules/Dashboard` — Owns navigation, module discovery, and Dashboard-local workspace session/event rows. It does not own users, roles, patients, clinical workflow state, treatment logic, admin-account logic, backup logic, or source-of-truth profile data.
- `Modules/Add New Patient` — Sole owner of durable Patient identity, the canonical `patientId` UUID, Encounter/intake identity, Follow-up Delta records, patient-code resolution, demographic validation, and intake snapshots. `patientCode` is a human-facing alias and must not be the cross-module key of record.
- `Modules/Diagnosis` — Owns diagnosis-assessment state, criteria evaluation, clinician decision state, assessment history, and diagnosis-domain audit snapshots. The criteria engine produces evidence; only the psychiatrist's explicit decision is the clinical assertion.
- `Modules/Severity` — Owns PANSS assessment data and scoring behavior. The current module is patient-code keyed and JSON-backed; the target boundary requires assessment, Patient, and Encounter UUIDs, server-side score recomputation, versioning, auth, CSRF, ETag/concurrency protection, and database persistence.
- `Modules/Medical History` — Owns medical-history submissions and its validation rules. The current six-character-code/JSON design is a prototype; the target boundary requires submission, Patient, and Encounter UUIDs, schema/version metadata, authenticated access, auditability, and server-side database persistence.
- `Modules/Suicide Risk` — Sole owner of encounter-scoped suicide-risk assessment records. Its v1 module stores explicit psychiatrist assertions only for the uncertainty and urgent states already accepted by the ownership and Treatment Plan safety-policy contracts, and publishes versioned Treatment Plan snapshots. No approved C-SSRS source/licensing contract, questions, scoring rules, negative/low-risk assertion, or instrument-completion claim exists; the module exposes that limitation and required risk-dependent processing fails closed.
- `Modules/DDI` — owner of Medication Knowledge, medication identity resolution, interaction-check behavior, knowledge-base versions/revisions, approval state, and DDI findings. Browser-local review, activation, and audit state are prototype-only and must move behind protected server APIs.
- `Modules/BN Manager` — Sole runtime owner of the four canonical BIF 0.3 XML models, the XSD, registry metadata, model validation, and posterior evaluation. It does not own patients, Dashboard state, treatment plans, or caller filesystems.
- `Modules/Treatment Plan` — Orchestrates authenticated REST reads from upstream owners; creates immutable Clinical Input Snapshots, Recommendation Runs, Primary Treatment Plans, structured Plan Edits, Safety Findings, Recommendation Evidence, immutable Final Treatment Plans, and supersession links. It must not mutate upstream Patient, Encounter, assessment, DDI knowledge, or BN model records.
- Follow-up is an orchestration flow across existing owner APIs, not a standalone data-owning module. Add New Patient creates the follow-up Encounter and owns its Follow-up Delta; assessment modules own new encounter-scoped assessments; Treatment Plan owns any superseding plan and its link. Follow-up-specific model assets do not establish another writer or service boundary.
- `BNs` — Clinical source excerpts, qualitative model specifications, diagrams, XML/NET artifacts, and model documentation. These are evidence/model-development assets. They become runtime-authoritative only when admitted to the owning module's versioned, validated, clinically governed registry.
- Root architecture/governance files — Define ubiquitous language, design tokens, context maps, model schemas, clinical safety boundaries, and unification rules. They are governance inputs, not runtime data stores.

## Storage Model

- **Module databases**: Each module owns its physical database, schema, migration history, credentials, backups, restores, retention rules, and repository adapter. SQLite files are physically separate. PostgreSQL deployment uses separate databases or schemas and credentials; no module may query another module's storage.
- **Authentication database**: Stores users, bcrypt password hashes, roles/account status, password-rotation state, server-side sessions, login-failure state, disclaimer versions/acceptances, schema version, and auth/security audit events. Raw JWTs, plaintext passwords, and secrets must not be logged or exposed.
- **Dashboard database**: Stores only Dashboard-local activation/session and workspace-event data. Authentication remains authoritative for identity and roles; clinical modules remain authoritative for workflow state.
- **Patient and Encounter storage**: Add New Patient stores durable Patient identity separately from Encounter/intake records. `POST /api/patients` may remain a convenience transaction that creates both, but downstream relations persist canonical UUIDs, not patient codes.
- **Assessment storage**: Diagnosis, Severity, and Medical History each own their assessment/submission records. Treatment Plan stores only stable references and immutable, versioned source snapshots with owner, schema version, resource version/ETag, retrieval time, and response hash.
- **Treatment-plan storage**: Stores immutable input snapshots, idempotent recommendation runs, Primary Plan versions, append-only structured edits, safety findings, evidence/provenance bundles, immutable Final Plans, and supersession relations. A finalized plan is never updated in place.
- **Bayesian-model registry**: BN Manager stores module-controlled relative registry paths to four canonical XML models plus `XSD.xml`. Model identity must include stable ID, version, and hash.
- **DDI knowledge storage**: The production target is server-side, role-protected, immutable revision storage with a lifecycle such as `draft -> reviewed -> active -> retired`, rollback, source/evidence metadata, medication identities, and knowledge-base version/hash. 
- **Browser storage**: Limited to non-PHI transient UI state and secure cookies. PHI, clinical recommendations, DDI audit records, patient codes used as integration keys, and authoritative clinical state must not be persisted in `localStorage`, URLs, query strings, filenames, caches, analytics, or unprotected downloads. Existing Severity/DDI browser-storage behavior is a known migration item.
- **Logs and provenance**: Security audit and clinical provenance are separate append-only concerns. Logs are redacted and must not contain secrets or PHI. Clinical artifacts retain actor, time, source owner, source/model/knowledge versions, accepted inputs, ignored/unresolved inputs, policy version, and correlation identifiers.

## Auth and Access Model

- Authentication is centralized. Browser and server consumers verify identity through the versioned Authentication session REST contract; they never read the auth database, import Authentication implementation code, or independently treat decoded JWT claims as current authority.
- Canonical roles are lowercase `admin` and `psychiatrist`; legacy `user` input is normalized to `psychiatrist` only for compatibility. Role values are controlled contract values, not free text.
- Login issues an HS256-signed JWT in an `HttpOnly`, `SameSite=Lax` cookie, with `Secure` required behind HTTPS. Authorization also checks the server-side session and current account state, so logout, disablement, role changes, and password reset can revoke access immediately.
- `GET /api/auth/session` is the trust seam and must return a versioned structured identity containing authenticated state, stable user UUID, username, canonical role(s), session UUID, expiry, disclaimer status, and password-change gates.
- Psychiatrist access is gated by active-account status, required password rotation, and acceptance of the active versioned clinical disclaimer.
- Cookie-authenticated state changes require signed double-submit CSRF protection. Each module owns its CSRF bootstrap/validation implementation while conforming to the common interface profile.
- Dashboard creates only a Dashboard-local session after validating Authentication and revalidates Authentication on protected requests. Request-body identity is ignored; identity comes from the trusted auth response.
- Clinical reads and writes are role-checked at the owning module. Patient creation and clinical decisions require psychiatrist authority; explicitly documented administrative reads/actions may permit `admin`. Admin account lifecycle operations remain inside Authentication.
- Internal service-to-service calls follow [ADR-0002](architecture-decisions/0002-internal-service-authentication.md): per-service HMAC-SHA256 assertions authenticate the caller, exact destination allowlists constrain outbound requests, and only the configured Authentication session cookie may be forwarded for user-attributed calls. Every protected target revalidates that opaque cookie through Authentication; background calls carry no user identity and cannot perform user-only actions. Request, correlation, and causation identifiers are propagated without PHI.
- Every denied access, privileged account action, session lifecycle event, and policy-approved clinical override is auditable. Security audit records and clinical rationale/provenance records remain distinct.

## Invariants

1. **Modules remain independent.** Every module must run and test independently. Cross-module communication is REST-only; cross-module source imports, shared domain implementations, database reads, filesystem access, and shared mutable files are forbidden.
2. **Every persisted entity has exactly one owner.** The owning module defines the canonical identifier, schema, validation, lifecycle, persistence, migrations, and authoritative REST representation. No code change may silently create a second writer.
3. **Canonical identity is UUID-based.** Patient, Encounter, assessment, recommendation, plan, session, model evaluation, and other durable entities use stable UUIDs where specified. `patientCode`, names, timestamps, medication display text, and other mutable aliases are never cross-module foreign keys of record.
4. **Every dataset and interface is versioned and validated.** Persisted and exchanged data declares a schema/interface/module version. Consumers validate responses before use or persistence and fail explicitly on unsupported major versions.
5. **Cached or copied upstream data is never authoritative.** A snapshot must retain source module, source identifier, schema version, resource version/ETag, retrieval time, and content hash. Upstream changes create a new snapshot and recommendation run; they do not rewrite history.
6. **The psychiatrist is the final clinical authority.** Diagnosis criteria, Bayesian posteriors, DDI alerts, and Primary Treatment Plans are decision support, not signed treatment orders. Clinician confirmation or modification is explicit and attributable.
7. **Final plans are immutable.** Finalization runs server-side safety revalidation and creates a new immutable Final Treatment Plan. Follow-up or correction creates a successor and preserves the prior plan, provenance, and edit ledger.
8. **Safety gates outrank probabilistic ranking.** Hard contraindications, severe DDI policy, crisis/emergency rules, allergy rules, and required-data checks cannot be bypassed by a favorable Bayesian posterior. Any policy-approved override requires an explicit rationale and audit/provenance record.
9. **Missing, stale, conflicting, ambiguous, or unresolved data is never silently guessed.** The system exposes the limitation, blocks or qualifies generation according to policy, and identifies the owning module/action needed to resolve it. An unresolved medication identity must never be reported as “no interaction.”
10. **PHI does not leak across trust boundaries.** PHI is excluded from URLs, query strings, browser storage, logs, analytics, caches, filenames, and unprotected exports. Transport is encrypted; production persistence, backups, and secrets require documented protection and access controls.
11. **One image is not one process or one codebase.** The unified Docker image contains separately configured module processes, ports/base paths, health/readiness checks, migrations, and writable data directories. Only the gateway is externally bound.
